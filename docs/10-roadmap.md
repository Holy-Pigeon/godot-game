## 0. 路线图的第一原则

> **先验证乐趣，再建平台。**

这个项目最大的失败模式是：花半年做出一个漂亮的关卡编辑器、LLM 主持人和轮回系统，
然后发现**底层的一局根本不好玩**。

因此整条路线图围绕一个判断点组织：

> **M0 唯一要证明的事：密令能把一个平庸玩法变成让人上头的社交博弈。**
> **如果 M0 不好玩，后面全部推翻重来，不要往上叠系统。**

## M-1 · 工程准备（M0 之前）

| 项 | 内容 |
|---|---|
| 工程配置 | 渲染方法降到 Mobile；纹理过滤 Nearest；视口 480×270；新增 dedicated server 导出预设 |
| 目录骨架 | 按 [09 §2](09-architecture.md) 建 `core/ server/ client/ content/ tests/ tools/` |
| 依赖检查 | CI 静态检查：`core/` 不得引用 `client/`、`server/` |
| 单测框架 | headless 跑 `core/` 纯逻辑测试 |
| 事件日志 | 事件总线 + 序列化 + 重放器（**从第一天就要有**，后补代价极大） |
| 本地化表 | 从第一行代码起不允许硬编码面向玩家的字符串 |

**完成判定**：能在 headless 下跑通一个"空关卡"的完整事件流，并重放出逐字节一致的结果。

**工作量级**：1–2 周。

## M0 · 垂直切片：密令验证

### 目标

用最小成本回答：**密令是不是真的好玩。**

### 交付物

| 模块 | 功能点 |
|---|---|
| 玩法 | **1 个基础玩法模板**：德州扑克变体（简化规则，回合明确，10 人桌） |
| 房间 | 10 人房间，ENet 局域网/直连即可，**不做匹配系统**（手动开房） |
| 密令 | 密令定义结构、**手工编写的 30 条密令池**、随机分配、达成判定、结算公开 |
| 经济 | 余命押注与瓜分（整数刻），双池结算（名次池 / 密令池） |
| 出局 | 出局即转观测者：可看部分隐藏信息、可下注、**每局一次的 30 字传声** |
| 表现 | 极简 UI（没有像素美术也行，先用 Godot 默认控件），**信息三分区**必须做 |
| 结算 | **全场密令公开的回放式结算**——这是 M0 的核心体验，必须做足 |

### 明确不做

轮回、庇护所、回响、生肖、LLM、AI 编号、UGC、编辑器、账号系统、美术。

### 核心假设与验证方式

| 假设 | 验证方式 | 通过标准 |
|---|---|---|
| 密令让平庸玩法变好玩 | **10 人真人内测，至少 12 局**，对照组：同样德州但无密令 | 有密令组的"还想再来一局"比例显著高于对照组 |
| 结算揭晓是"啊哈时刻" | 观察结算时的语音/文字反应 | ≥ 50% 的局在结算时出现明显的集体反应 |
| 密令达成率健康 | 数据统计 | 落在 35–55% 区间 |
| 单局时长可接受 | 计时 | 中位数 ≤ 40 分钟 |

### 回炉条件（重要）

- 若无密令组与有密令组的体验差异不明显 → **密令假设不成立**，整个项目要重新设计核心。
- 若单局超过 60 分钟 → 玩法模板选错，换更短的模板重测。
- 若玩家反馈"密令让我不想认真打牌" → 密令与基础玩法的耦合方式错了，需重设计密令类型分布。

**工作量级**：4–6 周。**这是全项目最重要的 6 周。**

## M1 · 规则引擎数据化

### 目标

把 M0 里硬编码的德州逻辑，抽成 `基础玩法模板 + 规则修正件` 的数据结构，证明**组合能产生内容**。

### 交付物

| 模块 | 功能点 |
|---|---|
| 引擎 | 触发器/效果的预定义清单（首批各 15–20 个）、条件求值、**优先级栈裁决器** |
| 模板 | **3 个基础玩法模板**：德州变体、投票放逐、盲拍卖 |
| 修正件 | 首批 **30 个规则修正件**，按十二权柄分类归档 |
| 关卡包 | 关卡包格式 v1 + 加载器 + 静态校验器 |
| 工具 | `tools/` CLI：校验关卡包、批量试跑（此时用脚本 AI，不用 LLM） |
| 内部编辑器 | 最简陋的表单式组合界面，**仅供内部策划用**，不对玩家开放 |

### 核心假设

| 假设 | 验证方式 | 通过标准 |
|---|---|---|
| 修正件组合能产出**质感不同**的关卡 | 内部策划用同一模板 + 不同修正件做出 6 个关卡，盲测 | 玩家能说出这几关"玩法感觉不一样" |
| 引擎的裁决是可理解的 | 观察玩家对"为什么"面板的使用 | 无人抱怨"莫名其妙就死了" |
| 关卡包校验能拦住坏关卡 | 故意构造死锁/必然屠杀的关卡包 | 校验器全部拦下 |

**工作量级**：6–8 周。

## M2 · AI 层：解决冷启动

### 目标

**让一个人也能随时开局。** 这是从"能玩"到"能上线"的关键跨越。

### 交付物

| 模块 | 功能点 |
|---|---|
| AI 网关 | 服务端代理、玩家自带 Key、加密存储、房间 token 预算、硬超时、**降级链** |
| AI 编号 | 补位 NPC：人格生成、密令执行（**策略脚本决策 + LLM 只负责发言表演**）、拟人化节奏 |
| AI 生肖 | 3 个权柄系的主持人人格（建议 巳·蛇 / 辰·龙 / 亥·猪）、裁量边界护栏、公开裁决记录 |
| 回响 v1 | **0 阶既视感 + 1 阶微响**；渴望值累积；4 种创伤 × 4 种应对 = 16 格执念矩阵 |
| 匹配 | 大厅 + 日层匹配雏形（此时"日"可先按房间难度标签模拟） |
| 传输 | 从 ENet 切换到 WebSocket（`server/net/` 抽象层此时兑现价值） |

### 核心假设

| 假设 | 验证方式 | 通过标准 |
|---|---|---|
| AI 编号足够像人 | 局后问卷："场上有几个 AI" | 猜对率接近随机水平 |
| AI 补位不破坏体验 | 对比全真人局与 5 真人 + 5 AI 局的评分 | 评分差距 < 15% |
| LLM 延迟不卡对局 | 压测 + 故意断网 | 降级链接管，**对局零中断** |
| 首次觉醒是高光时刻 | 新玩家观察 | 首次濒死觉醒后的次日回访显著高于未觉醒者 |

**工作量级**：8–10 周。

---

## M3 · 元游戏：长期目标上线

### 目标

给玩家一个玩到第 50 局的理由。

### 交付物

| 模块 | 功能点 |
|---|---|
| 轮回 | 十日结构、日层难度曲线、结算与记忆继承、**零冷却重开**、磨损 |
| 庇护所 | **2D 像素可走动场景**：交易、情报、道具、结盟、查看刻印与档案 |
| 前史 | 行为观测 → 碎片授予 → 2–3 种解读分支 → 执念成型 |
| 真相轴 | 记忆碎片、档案室、终焉之地主线的第一章 |
| 回响 v2 | 补齐 8 种创伤（32 格）；开放 **2 阶**；分化与进化 |
| 刻印 | 三形态（遗言 / 统计聚合 / 伪造）、采信回流经济闭环 |
| 回溯 | 复活道具 + 公开污点 |
| 美术 | 像素美术正式立项（此前一直用占位资源） |

### 核心假设

| 假设 | 验证方式 | 通过标准 |
|---|---|---|
| 三轴互相挤压产生有意义的取舍 | 数据：烧记忆 vs 留记忆的玩家分布 | 两类玩家都存在且都有可观留存，不是一边倒 |
| 前史让玩家产生身份认同 | 访谈 | 玩家能自发讲述"我的编号是个什么样的人" |
| 零冷却重开真的留住人 | 数据 | 死亡后 5 分钟内重开率 > 60% |
| 第 7 日回访率 | 数据 | > 25% |

**工作量级**：10–14 周。

---

## M4 · UGC 生态：平台化

### 目标

把内容产能从"我们做"变成"玩家做"。

### 交付物

| 模块 | 功能点 |
|---|---|
| 编辑器 | 玩家可用的关卡编辑器：修正件拖拽组合、密令池编辑、压制配置、实时校验 |
| 质量漏斗 | 沙盒房 → AI 试跑 → 小范围灰度 → 正式池；评分、热度、下架 |
| 创作者经济 | 造关者从对局抽成余命、**造关者声望**（独立于战绩的第二条声望轴）、经典关卡库 |
| 晋升生肖 | 权柄成型判定、晋升审核、席位管理、任期与消耗、**申诉与褫夺** |
| 收成 | 生肖的胜利指标与结算 |
| 回响 v3 | 开放 **3 阶共鸣**；**4 阶权柄作为手工设计的叙事内容** |
| 赛季 | 大终焉全服事件、赛季主题征稿 |

### 核心假设

| 假设 | 验证方式 | 通过标准 |
|---|---|---|
| 玩家做得出好关卡 | 首月 UGC 关卡的评分分布 | 至少有 10 个关卡进入长期高频池 |
| 抽成能激励创作 | 创作者留存 | 发布过关卡的用户次月留存显著高于均值 |
| 质量漏斗能拦住垃圾 | 玩家投诉率 | 正式池关卡的差评率 < 15% |
| 生肖不滥权 | 申诉与褫夺数据 | 褫夺率 < 10%，且申诉处理有实际效果 |

**工作量级**：12–16 周。

## 里程碑总览

| 里程碑 | 主题 | 核心假设 | 工作量 | 失败代价 |
|---|---|---|---|---|
| M-1 | 工程准备 | — | 1–2 周 | 低 |
| **M0** | **密令验证** | **平庸玩法 + 密令 = 好玩** | 4–6 周 | **致命：假设不成立则全盘重设计** |
| M1 | 引擎数据化 | 组合能产生内容 | 6–8 周 | 高：UGC 路线不成立 |
| M2 | AI 层 | AI 补位可解冷启动 | 8–10 周 | 高：10 人门槛无解 |
| M3 | 元游戏 | 三轴能留住人 | 10–14 周 | 中：可迭代补救 |
| M4 | UGC 生态 | 玩家能供给内容 | 12–16 周 | 中：可退回官方产内容 |

## 可玩性验证的通用方法

每个里程碑都必须做一次真人测试，不允许"内部觉得不错就过"。

| 项 | 要求 |
|---|---|
| **人数** | M0 至少 10 人 × 12 局；M1 起至少 20 人；M3 起至少 50 人 |
| **对照组** | 关键假设必须有对照（如 M0 的"有/无密令"） |
| **量化指标** | 对照 [01 §8 循环健康度指标](01-core-loop.md#8-循环健康度指标上线后监控) |
| **定性指标** | 局后 5 分钟自由讨论录音，统计"自发复盘"的比例——**玩家愿意复盘 = 局内有信息深度** |
| **回炉标准** | 每个里程碑预先写死"什么情况下推翻重做"，测试前就要写好，不许事后找补 |

## 未决问题

1. **M0 的玩法模板选德州是否最优？** 德州本身规则复杂、有牌运、上手门槛高。是否用"投票放逐"做 M0 更能凸显密令价值（更纯粹的社交，无牌运干扰）？倾向：**认真评估换成投票放逐**。
2. **M0 要不要做美术？** 完全无美术会影响测试者的沉浸感与评价效度，但做美术会拖慢生死判定点。倾向：用统一风格的占位素材，不做原创美术。
3. **M2 与 M3 的顺序能否互换？** 先做元游戏能更早看到长期留存数据，但没有 AI 补位就凑不齐人测。倾向：不换。
4. **人力假设**：以上工作量级基于 2–3 人全职。若是单人业余项目，M0 之后应考虑砍掉 M4 或大幅简化 M2。这需要尽早明确。
5. **公开测试的时机**：M2 结束（能自动开局）就小范围公测，还是等到 M3（有长期目标）？早测能拿数据，晚测能保口碑。
