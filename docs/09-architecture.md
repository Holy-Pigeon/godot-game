# 09 · 技术架构

> 状态：草案 v0.1 ｜ 关联：[07 关卡包与规则引擎](07-level-pack-and-rule-engine.md)、[08 UGC 与 AI 主持人](08-ugc-and-ai-host.md)、[10 路线图](10-roadmap.md)

**引擎基线**：Godot **4.8**，Forward+ 渲染，Windows 下 D3D12，物理 Jolt（见 `project.godot`）。
当前工程为空，只有 `icon.svg`。本文档定义从零搭起的骨架。

> 注：本作是 **2D 像素 + 回合制信息博弈**，Forward+ 与 Jolt 对我们几乎无用。
> 建议在 M0 之前把渲染方案降到 **Mobile / Compatibility**，物理留默认即可——见 §9.3。

---

## 1. 架构原则

| 原则 | 含义 | 违反的后果 |
|---|---|---|
| **服务器权威** | 所有胜负、余命、密令、回响判定只在服务端发生 | 客户端改内存即可作弊 |
| **确定性状态机** | 同样的种子 + 同样的事件序列 = 同样的结果 | 重放漂移，反作弊与复盘全废 |
| **表现层纯客户端** | 客户端不持有任何未公开的信息 | 抓包即可看到别人的密令 |
| **全对局可重放** | 种子 + 事件日志足以完整重建一局 | 无法做申诉、复盘、档案与自动化回归 |
| **core 不依赖引擎** | 规则逻辑是纯 GDScript/C# 数据处理，不 `get_node()` | 无法单测，无法在 headless 下跑 |

### 1.1 依赖方向（硬约束）

```
        ┌──────────┐        ┌──────────┐
        │  client  │        │  server  │
        └────┬─────┘        └────┬─────┘
             │                   │
             └────────┬──────────┘
                      ▼
                 ┌─────────┐        ┌────────┐
                 │  core   │◀───────│content │
                 └─────────┘        └────────┘
                      ▲
                 ┌────┴────┐
                 │   ai    │（只读 core 的公开视图）
                 └─────────┘
```

**`core/` 绝不允许 import `client/` 或 `server/` 的任何东西。** CI 里加静态检查。

## 3. 规则引擎

### 3.1 事件总线

- **同步、有序、单线程**。禁止在事件处理内做异步等待。
- 每个事件带 `seq`（全局递增）、`tick`、`actor`、`payload`。
- 总线的完整事件流即**对局日志**，落盘后可重放。

### 3.2 确定性红线

| 禁止 | 替代 |
|---|---|
| 无种子随机 | 每局一个 `master_seed`，派生子流（洗牌流 / 密令流 / AI 流互相独立） |
| 依赖 `Dictionary` 迭代顺序 | 一律显式排序后再遍历 |
| 依赖节点树遍历顺序 | core 层不碰节点树 |
| 浮点累加做经济计算 | 余命用**整数最小单位**（建议 1 日 = 100 刻） |
| 依赖真实时间 | 用逻辑 tick；倒计时由服务端广播 |

### 3.3 统一裁决管线（最大的工程红利）

[回响](04-echo.md)与[规则修正件](07-level-pack-and-rule-engine.md)是**同一种东西的两个来源**：

```
来源 A：关卡包的规则修正件（作者提供）
来源 B：玩家的回响           （前史生成）
        │
        └──▶ 同一套 Trigger → Condition → Effect 结构
                    │
                    ▼
              裁决器 Adjudicator
                    │
        ┌───────────┴───────────┐
        │   优先级栈（见下）      │
        └───────────┬───────────┘
                    ▼
              状态变更 + 事件广播
```

**优先级栈草案**（数字小者先结算，同级按 `seq` 升序稳定排序）：

| 优先级 | 层 | 说明 |
|---|---|---|
| 0 | **压制层** | 关卡的压制配置。先判断某回响是否被禁用 |
| 1 | **基础玩法模板** | 模板自身的核心规则 |
| 2 | **关卡规则修正件** | 作者挂载的修正件 |
| 3 | **回响 · 3 阶共鸣** | 修改规则本身，必须早于个体判定 |
| 4 | **回响 · 2 阶** | 改判、豁免、转嫁 |
| 5 | **回响 · 1 阶** | 只影响自己的信息层 |
| 6 | **密令判定** | 在结果确定后判定达成 |
| 7 | **经济结算** | 余命流转、抽成、收成 |

**冲突解决规则**：
1. 同优先级互斥效果 → 按 `seq` 先到先得，后者失效并记录"被压制"。
2. "禁止 X" 恒强于 "允许 X"（否定优先）。
3. 任何被压制/失效的效果**必须产生一条公开事件**——玩家要能看到"我的回响被吃了"。

## 4. 网络模型

### 4.1 关键判断：同步的是**事件**，不是帧

本作是回合制信息博弈，**没有实时物理同步需求**。带宽与延迟压力极低（庇护所的走动除外）。

| 场景 | 同步方式 | 频率 |
|---|---|---|
| 关卡内 | 事件驱动 RPC，服务端广播裁剪后的事件 | 每次行动 |
| 庇护所走动 | 低频位置同步（4–10 Hz）+ 客户端插值 | 持续 |
| 观测者 | 只订阅"观测者视图"事件流 | 事件驱动 |

### 4.2 传输选型

| 方案 | 评价 |
|---|---|
| Godot 高层多人 API + ENet | M0 最快落地，适合内网/小规模验证。**推荐用于 M0–M1** |
| WebSocket（Godot 原生支持） | 便于未来 Web 导出与穿透代理，**推荐 M2 起作为正式传输** |
| 自建 TCP/QUIC 协议 | 收益不足以覆盖成本，不做 |

**建议**：M0 用 ENet 快速验证；**在 `server/net/` 做传输抽象层**，M2 平滑切到 WebSocket，避免返工。

### 4.3 视图裁剪（反作弊的命门）

> **服务端向每个客户端发送的事件，必须经过按玩家的视图裁剪。**

| 数据 | 下发给谁 |
|---|---|
| 自己的密令 | 仅本人 |
| 他人的密令 | **任何人都不下发**，直到结算或被公开 |
| 手牌 / 隐藏信息 | 仅持有者（+ 有权限的观测者） |
| 回响的存在与内容 | 未发动时**不下发**；发动后全场 |
| 前史与记忆碎片 | 仅本人 |

**绝不允许"下发了但客户端不显示"这种做法。**

### 4.4 房间生命周期

```
创建 → 招募（等待玩家 / 触发 AI 补位）→ 锁定名单 → 发牌与密令分配
    → 回合循环 → 结算 → 日志落盘 → 销毁
```

- **AI 补位触发条件**：等待超过 T 秒（建议 45s）且人数 ≥ 下限（建议 4 真人）→ 用 AI 编号填满至 10。
- **断线**：进入 AI 托管（保守策略），并按时长扣余命；重连后立刻收回控制权。
- **托管的道德边界**：托管 AI **不得读取该玩家的密令做最优决策**，只做保守行动（跟注/弃权/沉默）。

## 5. 数据与持久化

### 5.1 实体清单

| 实体 | 关键字段 | 说明 |
|---|---|---|
| `Account` | id, 认证信息, 创建时间, 封禁状态 | 账号 |
| `Numbering`（编号） | id, account_id, 编号显示名, 磨损次数, 声望, 消极标记 | 玩家的持久身份 |
| `Run`（轮回） | id, numbering_id, 当前日, 余命, 状态, 开始/结束时间 | 一次 run |
| `PrehistoryNode` | id, numbering_id, 创伤类型, 应对方式, 解读选择, 揭示时间 | 前史片段 |
| `MemoryShard` | id, numbering_id, 类型, 内容引用, 是否失真, 是否已烧 | 记忆碎片 |
| `Echo` | id, numbering_id, 权柄系, 阶, 触发条款集, 效果引用, 暴露状态 | 玩家的回响 |
| `DesireMeter` | numbering_id, 创伤类型, 累积值, 衰减时间戳 | 渴望值（按创伤分桶） |
| `LevelPack` | id, 作者, 版本, 基础模板, 修正件列表, 密令池, 压制配置, 状态 | 关卡包 |
| `Match`（对局） | id, pack_id, 参与者, 种子, 开始/结束, 结果摘要 | 一局 |
| `MatchLog` | match_id, 事件流（压缩） | 重放源 |
| `Engraving`（刻印） | id, 作者编号, 类型, 内容, 被采用次数, 回流余命 | 死者留下的痕迹 |
| `LedgerEntry` | id, 编号, 变动量, 原因, match_id, 时间 | 余命流水（审计用） |
| `ZodiacSeat` | 权柄系, 当前持有者, 任期, 收成累计, 申诉记录 | 生肖席位 |

### 5.2 存储建议

- **关系型数据库**做账号/经济/档案（余命必须有**完整流水台账**，可对账）。
- **对象存储/文件**放对局日志（体积大、只追加、冷读）。
- **缓存**放大厅与匹配状态。
- 余命的每一次变动都必须写 `LedgerEntry`，**任何余命变动不留痕即视为 bug**。

## 6. AI 网关

> 完整设计见 [08](08-ugc-and-ai-host.md)，这里只说工程形态。

```
房间 ──▶ ai/gateway ──▶ 供应商适配层 ──▶ 玩家自带 Key 的外部 API
             │
             ├── 预算控制（按房间 token 上限）
             ├── 限流与超时（硬超时，建议 8s）
             ├── 内容过滤（进出双向）
             └── 降级链：LLM → 预生成文本库 → 纯模板文本
```

**硬性要求**：

1. **客户端绝不直连 LLM**（Key 泄露 + 篡改）。Key 加密存储于服务端，仅解密于内存。
2. **AI 调用失败或超时不得阻塞对局** —— 降级链必须在超时瞬间接管。
3. AI 的输出**不能直接改变游戏状态**，只能提交"提议"，由 core 的裁决器按预设边界过滤后执行。
4. 所有 AI 提议与裁决结果**全场可见并入日志**，用于申诉。

## 7. 客户端表现层

### 7.1 场景划分

| 场景 | 内容 | 技术要点 |
|---|---|---|
| `shelter/` | 庇护所，2D 像素可走动 | TileMapLayer + CharacterBody2D + Y-sort；低频网络同步 |
| `level/` | 关卡表现层，按基础玩法模板一个场景 | 纯 UI 驱动 + 少量演出；**不含任何规则逻辑** |
| `observer/` | 观测者视角 | 复用 level 场景 + 额外信息层 + 下注 UI |
| `archive/` | 档案、真相轴、前史、刻印 | 大量文本排版，重信息设计 |
| `editor/` | 关卡编辑器（M4） | 修正件拖拽组合 + 实时校验 |

### 7.2 信息呈现原则

> **这类游戏 90% 的体验在信息呈现。UI 就是我们的核心玩法界面，不是外壳。**

| 原则 | 落地 |
|---|---|
| 三层信息分区 | **公开区**（所有人可见）/ **私密区**（只有我）/ **推测区**（我的笔记与标记） |
| 可回溯 | 任何时刻可翻阅本局完整公开记录，禁止"错过就没了" |
| 玩家笔记 | 允许对每个编号打标签、记颜色、写备注，并**跨轮回保留**（这是"记忆"的 UI 化身） |
| 裁决透明 | 每次裁决弹出可展开的"为什么"，列出触发的修正件/回响与优先级 |
| 演出不阻塞 | 觉醒/裁决动画可跳过，不占用决策时间 |

### 7.3 像素规格建议

- 基准分辨率 **480×270**（16:9），整数倍缩放到 1920×1080。
- `project.godot` 已设 `stretch/mode=canvas_items` + `aspect=expand`，需补 `viewport` 相关配置与 `texture_filter=Nearest`。
- 角色 32×32，场景瓦片 16×16。

## 8. 可测试性

| 层 | 手段 |
|---|---|
| `core/` | **纯逻辑单元测试**（GUT 或自研 headless runner）。目标覆盖率 ≥ 80% |
| 规则引擎 | **重放回归**：保存历史对局日志，每次改动后重放，结果必须逐字节一致 |
| 关卡包 | `tools/` 提供 CLI：静态校验 + 用 AI 编号跑 N 局蒙特卡洛，输出致死率/时长/密令达成率 |
| 平衡数值 | 批量试跑生成分布报告，与 [01](01-core-loop.md) 的健康度指标对照 |
| 压测 | 用 AI 编号开满房间，压服务端房间数上限 |

**重放一致性是本项目的生命线**：它同时服务反作弊、申诉、档案内容和数值调优。
一旦出现漂移，必须当作 P0 处理。

## 9. 工程约定

### 9.1 GDScript vs C#

| 建议 | 理由 |
|---|---|
| **全项目 GDScript 起步** | 迭代快、无额外运行时、社区资源多；本作没有 CPU 密集计算 |
| 若 `core/` 后期出现性能瓶颈或需要严格类型 | 再局部迁移到 C#，因为 core 是纯逻辑，迁移成本可控 |

**不要一开始就上双语言。**

### 9.2 命名与代码规范

- 文件与目录 `snake_case`，类名 `PascalCase`，常量 `SCREAMING_SNAKE_CASE`。
- `core/` 内一律**静态类型标注**（`func f(x: int) -> bool`），关掉动态类型的便利以换取可维护性。
- 所有面向玩家的字符串走**本地化表**，从第一行代码开始，不允许硬编码中文。
- 关卡包与存档格式**必带 `schema_version`**，且 `packfmt/` 提供迁移函数链。

### 9.3 project.godot 待调整项

| 项 | 当前 | 建议 | 理由 |
|---|---|---|---|
| 渲染方法 | Forward+ | **Mobile** 或 Compatibility | 2D 像素游戏不需要 Forward+，且能大幅降低启动开销与硬件门槛 |
| 物理引擎 | Jolt (3D) | 保持默认 | 我们只用 2D 物理做庇护所碰撞 |
| 纹理过滤 | 默认 | **Nearest** | 像素风必须 |
| 视口 | 未设 | 480×270 + `viewport` 拉伸 | 像素完美 |
| headless 导出预设 | 无 | 新增 **dedicated server** 预设 | `server/` 需要独立导出 |

### 9.4 版本控制

`.gitignore` 已存在，需确认包含 `.godot/`（导入缓存与 shader cache 不入库）。
对局日志、玩家数据、API Key **一律不入库**。

## 10. 未决问题

1. **服务端是否必须用 headless Godot？** 用 Godot 可以让 `core/` 代码在客户端与服务端完全复用（巨大优势），但在运维、水平扩展、可观测性上不如 Go/Node。倾向：**M0–M2 用 headless Godot**，若规模上来再把大厅/匹配拆成独立服务，房间进程仍留 Godot。
2. **余命的最小单位与整数化方案**：1 日 = 100 刻是否足够？涉及抽成比例与小额交易的精度，定错了后期迁移很痛。
3. **对局日志的体积与保留期**：全事件日志 × 大量对局的存储成本；保留多久？是否只对"有申诉/高评分"的对局长期保留？
4. **庇护所的同房人数上限**：可走动场景里同屏多少个编号？超过后分片还是分房？这直接影响社交密度与网络成本。
5. **关卡包的分发方式**：随客户端下载，还是运行时从服务端拉取？后者利于热更与下架，但要求关卡包完全数据化且客户端有通用渲染器——这反过来约束了 [07](07-level-pack-and-rule-engine.md) 的格式设计。
