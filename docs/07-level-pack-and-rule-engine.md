# 关卡包格式与规则引擎

> 状态：草案 v0.1 | 关联：[核心循环](01-core-loop.md)、[密令系统](03-mandate.md)、[回响系统](04-echo.md)、[十二权柄与生肖](05-zodiac-authority.md)、[UGC 生态与 AI 主持人](08-ugc-and-ai-host.md)

## 0. 本文档的地位

**关卡**是《终焉之地》所有玩法的容器。编号在关卡里押上余命、执行密令、被迫背叛、觉醒回响。因此关卡的表达能力决定了这款游戏内容的上限，而关卡的**安全边界**决定了这款游戏能否活过第一次 UGC 开放。

本文档定义两样东西：

1. **关卡包（Level Pack）** —— 一个关卡的完整数据描述，可提交、可校验、可分发、可版本化。
2. **规则引擎** —— 服务器权威地执行关卡包、裁决一切结果、产出可重放日志的确定性状态机。

## 1. 设计哲学与安全边界

### 1.1 第一原则：不要让玩家"写游戏"，让他们"改规则"

绝大多数 UGC 平台的失败姿势是"给玩家一个引擎"。结果是 99% 的投稿不可玩，1% 的精品被淹没，平台变成废墟仓库。

我们采取相反的姿势：

> **玩家拿到的不是白纸，而是一张已经很好玩的牌桌，以及一盒可以往桌上扔的规则。**

具体拆解为一条公式：

```
关卡包 = 基础玩法模板(Base Game)
       + 规则修正件(Modifier) × N
       + 主持人人格(生肖 Persona)
       + 密令池(Mandate Pool)
       + 压制配置(Suppression)
```

- **基础玩法模板**由官方设计并长期打磨，保证**可玩性下限**。作者不能修改其核心状态机。
- **规则修正件**是作者真正的创作空间，通过组合产生**内容深度上限**。
- **密令池**决定这一关的人性走向——同一个德州变体，配上"保护某人"的密令池和配上"必须让某人死"的密令池，是两款完全不同的游戏。
- **压制配置**决定回响者在这一关有多大呼吸空间。
- **主持人人格**决定叙事气质，由生肖权柄限定。

作者的创作动作因此从"编程"降维成"**配置 + 组合 + 调味**"。这既降低了创作门槛，又抬高了创作质量的地板。

### 1.2 第二原则：绝不允许 UGC 提交任意 GDScript

这条是**红线，不接受任何形式的妥协**。

在服务器权威架构下执行玩家提交的脚本，等于把服务器的进程内存、文件系统、网络出口、其他玩家的隐藏信息（手牌、密令、回响状态）全部交给一个匿名投稿者。GDScript 没有可信的沙箱模型，`load()`、`FileAccess`、`OS`、反射式属性访问都无法在语言层面被可靠剥离；即使做出一个白名单解释器，其攻击面也远大于收益。

因此：

| 允许 | 禁止 |
|---|---|
| 从**预定义触发器**中挑选 | 自定义触发时机 |
| 从**预定义效果**中挑选 | 自定义效果实现 |
| 填写受类型与值域约束的**参数** | 任意表达式、任意字符串求值 |
| 编写**纯展示用文本**（描述、旁白、密令文案） | 任何形式的代码、模板求值、外部引用 |
| 用**声明式条件**组合判断 | 循环、递归、跳转、自定义函数 |

修正件本质上是**数据**：一条 `触发器 → 条件 → 效果` 的记录。引擎读取数据、执行自己实现的逻辑。玩家永远无法让服务器运行"玩家写的东西"。

### 1.3 第三原则：回响与修正件共用同一套引擎

这是整个技术架构最大的**工程红利**，必须在第一天就锁死。

**回响**（玩家的超能力）与**规则修正件**（关卡作者的创作）在效果层面是同构的：两者都是"在某个时机，对局面施加一个规则性的改变"。

| | 规则修正件 | 回响 |
|---|---|---|
| 来源 | 关卡作者 | 玩家（由执念与前史生成） |
| 触发 | 关卡规则自动触发 | 玩家主动发动（需满足触发条件） |
| 归属 | 十二权柄之一 | 十二权柄之一 |
| 执行路径 | **同一条事件总线** | **同一条事件总线** |
| 裁决 | **同一套优先级栈** | **同一套优先级栈** |
| 日志 | **同一份事件日志** | **同一份事件日志** |

因此我们只需要实现**一套**触发器/条件/效果体系。新增一个效果原语，同时惠及关卡创作和回响设计。回响的分阶（微响 / 回响 / 共鸣 / 权柄）恰好对应**效果原语能触及的层级**（见 §3.3），这让回响的强度分级在工程上有了一个天然、清晰、不可绕过的定义。

**副产品**：压制（关卡对回响的封锁）在引擎里只是"对某一来源的修正件做准入过滤"，实现成本极低。

## 2. 基础玩法模板库

### 2.1 模板的定义

一个基础玩法模板是一台**官方实现的确定性状态机**，包含：

- 固定的阶段流转（如：发牌 → 下注轮 → 摊牌 → 结算）
- 固定的合法行动集合（如：跟注 / 加注 / 弃牌）
- 固定的胜负与结算判定
- 一组**挂载点**（Hook Point），即修正件可以介入的时机

作者选择模板后，只能通过修正件、密令池、压制、押注参数来改变它。核心状态机不可编辑。

### 2.2 首批模板候选（10 个）

| # | 模板 | 人数区间 | 单局时长 | 核心张力 | 适合挂载的修正件方向 | 优先级 |
|---|---|---|---|---|---|---|

| T-02 | **投票放逐** | 8–16 | 20–30 分钟 | 舆论、串供、公开处刑 | 辰·龙（改律）、戌·狗（契约）、申·猴（诡辩） | **M0** |

### 2.3 逐个说明

**T-01 德州扑克变体（M0 首发）**
选它作为第一个模板不是因为它好玩，而是因为它是**最好的测试床**：规则被全世界验证过、结算完全确定、信息不对称天然存在、且**足够"平庸"**——如果加上密令池后它变得好玩，就证明我们的密令系统真的有效。这是 M0 垂直切片的核心假设验证。

**T-02 投票放逐（M0 首发）**
提供与德州完全互补的张力：德州是"我和牌与筹码博弈"，投票是"我和人博弈"。它是**发言、串供、公开处刑**的载体，也是回响 3 阶效果（改写规则）最容易产生名场面的舞台。

**T-03 盲拍卖**
把余命直接变成出价筹码，让"我到底还剩几天可以烧"成为每一次出价的心理负担。适合挂"最低出价者扣余命""出价必须公开身份"等修正件。

**T-04 囚徒困境网格**
每回合与不同对手配对，多轮重复。它是**结盟与报复链**的纯粹形态，也是"戌·狗契约"类修正件的最佳容器。局时短，适合作为轮回中的"日"节奏调剂。

**T-05 密室搜证**
唯一强依赖 2D 像素场景走动的模板，与庇护所共用场景系统。信息以"物件"形式散布，可被藏匿、伪造、垄断。

**T-06 俄罗斯轮盘**
最短、最残酷、最适合作为第 7–9 日高致死率关卡。修正件方向偏向"谁来替你开枪""能否把枪口转向他人"。

**T-07 协作拼图**
表面是全员共赢，实则密令池中埋有破坏者。它是检验"密令能否把合作玩法变成猜疑玩法"的试金石。

**T-08 信息竞价**
把"情报"做成可交易商品，与庇护所的情报买卖打通。适合作为"刻印"内容的分发场景。

**T-09 排位淘汰赛**
适合大房间（20+），用于全服"大终焉"事件的骨架。

**T-10 契约谈判**
纯社交模板，几乎没有随机性。契约由引擎强制执行（违约自动扣余命），因此"敢不敢签"成为唯一的博弈。它是戌·狗系生肖的主场。

## 3. 规则修正件的结构

### 3.1 五元组

一条修正件由五部分组成：

```
修正件 = 触发器(Trigger)
       + 条件(Condition) × N     [合取]
       + 效果(Effect) × N        [有序执行]
       + 可见性(Visibility)
       + 归属权柄系(Authority)
```

| 部分 | 说明 |
|---|---|
| **触发器** | 引擎在什么时机检查这条修正件。**只能从预定义清单中选择**。 |
| **条件** | 触发后是否真的执行。多条条件之间为**合取（AND）**，需要"或"时拆成多条修正件。 |
| **效果** | 执行什么。多条效果按声明顺序依次执行，允许中途因失败而中断。 |
| **可见性** | 这条规则对谁公开。见 §3.4。 |
| **归属权柄系** | 决定这条修正件属于十二权柄中的哪一系，影响关卡的权柄标签与可用性。 |

### 3.2 首批触发器清单

| 触发器 | 时机 | 可用上下文 |
|---|---|---|
| `回合开始` | 每回合起始 | 回合数、存活编号列表 |
| `回合结束` | 每回合结算后 | 本回合全部行动记录 |
| `阶段进入` | 模板阶段流转时 | 阶段名 |
| `阶段离开` | 阶段结束时 | 阶段名、阶段内摘要 |
| `玩家行动前` | 某编号即将行动 | 行动者、拟执行行动 |
| `玩家行动后` | 某编号完成行动 | 行动者、行动结果 |
| `发言时` | 编号发出公开发言 | 发言者、发言内容元数据 |
| `押注时` | 编号押上余命/筹码 | 押注者、数额 |
| `弃权时` | 编号放弃行动 | 放弃者 |
| `投票结算` | 一轮投票统计完成 | 票型分布、结果 |
| `出局判定` | 引擎判定某编号出局 | 出局者、致因、致因来源 |
| `余命变动` | 任意余命增减 | 变动者、数额、来源 |
| `密令达成` | 某编号密令完成 | 达成者、密令类型（视可见性） |
| `密令失败` | 某编号密令确定失败 | 失败者 |
| `回响发动` | 任意回响被发动 | 发动者、回响阶数、权柄系 |
| `回响被压制` | 回响因压制未生效 | 尝试者、压制类型 |
| `信息揭示` | 任意隐藏信息转为公开 | 信息标识、揭示范围 |
| `契约缔结` | 引擎登记一份契约 | 缔约双方、条款 |
| `契约违约` | 契约条款被违反 | 违约者、条款 |
| `关卡开始` | 首回合前 | 全部参与编号 |
| `关卡结束` | 结算前 | 存活者、收成初值 |
| `倒计时归零` | 任意计时器到期 | 计时器标识 |

**设计约束**：触发器清单是**封闭集合**。新增触发器属于引擎版本升级，需要官方实现与回归测试，不能由作者定义。

### 3.3 首批效果清单

效果按**能触及的层级**分级，这个分级同时定义了回响的阶数上限：

**L1 · 信息层**（对应回响 1 阶「微响」）

| 效果 | 说明 |
|---|---|
| `揭示信息` | 把某项隐藏信息对指定范围公开 |
| `隐藏信息` | 使某项本应公开的信息不进入记录 |
| `伪造记录` | 向公开记录写入一条不实条目（须标注可被识破的途径） |
| `重播发言` | 令某条历史发言再次对全场呈现 |
| `私密传讯` | 在两名编号之间建立一次性单向信息通道 |
| `标记` | 给某编号附加一个可见/不可见的标签 |

**L2 · 判定层**（对应回响 2 阶「回响」）

| 效果 | 说明 |
|---|---|
| `扣减余命` | 直接扣除指定编号的余命 |
| `增加余命` | 反向操作，通常来自资源池而非凭空产生 |
| `强制行动` | 剥夺选择权，令某编号执行指定行动 |
| `禁止行动` | 移除某编号的某类合法行动 |
| `改判` | 覆盖一次已产生的判定结果 |
| `转嫁` | 把某编号承受的代价按比例转移给他人 |
| `豁免` | 使一次出局判定或代价判定失效 |
| `延迟结算` | 把一次结算推迟到指定时机 |

**L3 · 规则层**（对应回响 3 阶「共鸣」）

| 效果 | 说明 |
|---|---|
| `修改规则参数` | 改变模板暴露的数值参数（回合数、上限、阈值） |
| `启用/禁用行动类型` | 全局开关某类合法行动 |
| `注入密令` | 向指定编号追加一条新密令 |
| `撤销密令` | 使某条密令失效 |
| `变更胜负条件` | 替换本关的结算判据 |
| `变更压制` | 临时提升或解除对回响的压制 |
| `插入阶段` | 在流程中插入一个额外阶段 |

**L4 · 权柄层**（仅生肖可用，对应回响 4 阶「权柄」）

| 效果 | 说明 |
|---|---|
| `对他人施加规则` | 令某编号在后续若干关卡内携带一条个人规则 |
| `裁量` | 对模糊条款作出具有约束力的解释（须留裁决记录） |
| `褫夺` | 暂时剥夺某编号的回响使用资格 |
| `收成调节` | 调整本关收成的计算权重（受审计） |

### 3.4 可见性

| 可见性 | 说明 | 典型用途 |
|---|---|---|
| `公开` | 关卡开始时全场可见 | 主规则，公平竞技 |
| `延迟公开` | 首次触发后转为公开 | 陷阱型规则，触发即示众 |
| `定向` | 仅特定编号可见 | 与密令配合的私人规则 |
| `隐秘` | 全程不公开，仅在事后档案中可查 | 慎用，需通过审核（见 §7） |

**准入约束**：`隐秘` 可见性的修正件在一个关卡包中**不得超过 2 条**，且不得使用 L2 及以上的 `扣减余命` / `强制出局` 类效果。理由：不可知的致死规则会摧毁玩家对系统公平性的信任，这是社交博弈游戏的生命线。

### 3.5 组合爆炸如何产生内容深度

首批规模：**22 个触发器 × 约 25 个效果 × 条件与参数空间**。

即使只考虑"单触发器 + 单效果 + 一组参数"的最简修正件，也已有数百个语义清晰的组合；而一个关卡包可挂载 3–8 条修正件，且它们之间会**互相咬合**（一条修正件的效果可以成为另一条的触发条件）。

举例说明深度来源：

> **修正件 A**：`弃权时` → `扣减余命(1)`
> **修正件 B**：`余命变动` 且 变动为负 → `揭示信息(该编号的一条密令线索)`
>
> A 与 B 单独看都很朴素。合在一起，"弃权"变成了"公开泄露自己的秘密"——弃权从一个消极选项变成了**社会性死亡的开关**。作者没有写任何代码，但创造了一条全新的心理压力线。

这就是我们要的：**深度来自组合，不来自表达能力**。

## 4. 关卡包的字段结构

### 4.1 结构示意

```
LevelPack
├── meta            元信息
├── base            基础玩法模板引用与参数
├── modifiers[]     规则修正件列表
├── mandate_pool    密令池
├── suppression     压制配置
├── authority       生肖归属
├── stakes          押注参数
├── host_persona    AI 主持人人格设定
└── version         版本与兼容性
```

### 4.2 元信息 `meta`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `pack_id` | 标识符 | 是 | 全局唯一，由平台生成 |
| `title` | 文本 | 是 | 关卡名，上限 24 字 |
| `author_id` | 标识符 | 是 | 造关者编号 |
| `summary` | 文本 | 是 | 一句话简介，上限 60 字 |
| `briefing` | 长文本 | 是 | 开场规则说明（对玩家公开的部分） |
| `tags` | 标签数组 | 否 | 用于检索与推荐 |
| `day_tier` | 枚举 | 是 | 试炼层 / 倾轧层 / 崩坏层 / 终焉 |
| `expected_duration` | 整数（分钟） | 是 | 用于匹配与排期 |
| `content_rating` | 枚举 | 是 | 内容分级 |

## 5. 压制：不是补丁，是难度维度

### 5.1 问题

回响是玩家私有的规则例外权。关卡作者在设计时**无法预知**进场的十名编号带着什么回响。一个精心设计的投票放逐关卡，可能被一名辰·龙系 3 阶回响者一句话摧毁。

### 5.2 错误的解法

- 全局削弱回响 → 玩家几十小时的追求变成废纸，权柄轴崩塌。
- 让作者逐条禁用具体回响 → 作者不可能穷举，且会演变成军备竞赛。

### 5.3 正确的解法：把压制变成关卡的公开标签

压制不是"防止关卡被破坏的补丁"，而是**与人数、时长、致死率并列的第四个难度维度**。它被公示在关卡卡片上，是玩家选关时的核心决策依据。

| 压制模式 | 体验 | 适用场景 |
|---|---|---|
| **无压制** | 超能力者的修罗场。回响满天飞，局面极度不可预测 | 高日数关卡、赛季特别活动、回响者专场 |
| **部分封锁** | 只封某几系。例如封锁巳·蛇后，"没人能伪造信息"本身就是一条重要情报 | 主流配置，作者的主要调味手段 |
| **代价加重** | 回响可用，但烧掉的记忆翻倍。逼迫回响者做"值不值"的抉择 | 中高难度关卡的默认选项 |
| **绝缘区** | 回响完全失效。所有人回到赤手空拳 | 试炼层教学关；以及**最恐怖的高日数关卡** |

### 5.4 为什么"绝缘区"是恐怖的而不是无聊的

对普通编号，绝缘区意味着公平。
对回响者，绝缘区意味着**他赖以为生的东西被拿走了**——而他之所以成为回响者，正因为他曾被逼到绝境。绝缘区把他重新推回那个位置。

这在体验上制造了一个漂亮的反转：**越强的玩家，越怕这类关卡**。它天然地为高阶玩家提供了难度，而不需要任何数值堆砌。

### 5.5 引擎实现

压制在引擎里是**准入过滤器**，位于事件总线的入口：

```
回响发动请求 → 压制过滤器 → [通过] → 进入统一的裁决优先级栈
                          → [拦截] → 触发 `回响被压制` 事件 → 记入日志与档案
```

被压制的发动**依然产生事件**。这一点很重要：全场会看到"有人试图发动回响但失败了"（若压制配置为公示），这本身就是一条极有价值的社交信息——**你暴露了自己是回响者，却什么都没得到**。

## 6. 规则引擎的确定性要求

### 6.1 三条不可协商的工程约束

**约束一：服务器权威。**
所有判定、随机数、隐藏信息只存在于服务器。客户端是纯表现层，只接收"它有权知道的"事件切片。客户端永远不持有其他编号的手牌、密令、回响状态。

**约束二：确定性。**
给定 `初始种子 + 关卡包 + 有序输入事件列表`，引擎必须产出**逐位一致**的结果。这要求：

- 所有随机数来自单一可播种的伪随机流，按固定顺序取用。
- 禁止在规则逻辑中使用浮点累加、字典/哈希表的遍历顺序、系统时间、并行调度顺序。
- 所有集合运算在规则层使用**稳定排序**，排序键包含编号 ID 作为最终 tiebreaker。

**约束三：全对局可重放。**
每一局产出一份**事件日志**：种子 + 关卡包哈希 + 引擎版本 + 全部输入事件（含时间戳）+ 全部裁决结果。任何一局都可以在任何时候被重新执行。

### 6.2 可重放带来的四项收益

| 收益 | 说明 |
|---|---|
| **反作弊** | 客户端上报的行动与服务器重放结果不一致即为异常 |
| **复盘** | 玩家可回看整局，包括自己当时不知道的信息（死后解锁） |
| **档案内容** | 轮回结算时自动生成"档案"，是记忆碎片与刻印的素材来源 |
| **关卡校验** | 新关卡包提交后，用 AI 编号批量试跑，全部可重放、可统计 |

### 6.3 裁决优先级栈

当一个触发器时刻同时激活了多条修正件与多个回响时，必须有一个**完全确定、且玩家可理解**的排序规则。草案如下（自上而下依次执行）：

| 层级 | 类别 | 说明 |
|---|---|---|
| **P0** | 引擎硬约束 | 余命下限、单局损失上限、反作弊拦截。不可被任何来源覆盖 |
| **P1** | 压制过滤 | 决定哪些回响根本不进入后续流程 |
| **P2** | 生肖裁量（4 阶权柄） | 主持人的当场裁决。**须留公开裁决记录** |
| **P3** | 回响 3 阶（共鸣） | 规则层改动，先于一切具体判定生效 |
| **P4** | 关卡修正件 · L3 规则层 | 作者设定的规则层改动 |
| **P5** | 回响 2 阶（回响） | 判定层介入：豁免、改判、转嫁 |
| **P6** | 关卡修正件 · L2 判定层 | 作者设定的判定层效果 |
| **P7** | 基础模板原生判定 | 模板自身的胜负与结算逻辑 |
| **P8** | 回响 1 阶 & 修正件 L1 信息层 | 信息的揭示与隐藏 |
| **P9** | 密令达成检查 | 在局面稳定后统一结算 |
| **P10** | 日志与档案写入 | 最后写入，不影响任何判定 |

**同层冲突的决胜规则**（依次比较，直到分出先后）：

1. 阶数/层级更高者优先
2. **代价更大者优先**（烧掉更多记忆、付出更多余命的一方胜出——贯彻"代价换权力"的设计哲学）
3. 发动时刻更早者优先（服务器接收时序）
4. 编号 ID 字典序（最终 tiebreaker，保证确定性）

**互斥效果的处理**：当两个效果在语义上直接冲突（如 A 要求"某编号出局"、B 要求"豁免该出局"），按上表决出胜者后，**败者的效果被标记为"被压过"并记入日志**，其代价（记忆、余命）**照常扣除**。理由：底牌打出去就是打出去了，这是社交博弈的一部分，也防止玩家用"必定被抵消"的方式零成本试探。

**递归深度限制**：一条效果可能触发新的触发器（如 `扣减余命` 触发 `余命变动`）。引擎设定**最大级联深度为 4**，超出后剩余触发被丢弃并记入日志告警。关卡包静态校验会尝试检测潜在的无限级联（见 §7.1）。

## 7. 校验与准入

关卡包从提交到进入正式池，必须通过**四道闸门**。

### 7.1 闸门一：静态校验（自动，秒级）

| 检查项 | 说明 | 失败处理 |
|---|---|---|
| **模式合法性** | 字段类型、必填、值域、枚举合法性 | 拒绝 |
| **引用完整性** | 所有 `modifier_id` / `template_id` 存在且版本兼容 | 拒绝 |
| **级联环检测** | 构建"效果 → 触发器"有向图，检测强连通分量 | 存在环则警告并强制标注 |
| **死锁检测** | 是否存在"所有编号都无合法行动"的可达状态 | 拒绝 |
| **必然屠杀检测** | 是否存在"无论如何操作全员出局"的路径占比过高 | 拒绝或强制降级到高日数层 |
| **必然无人出局检测** | 是否存在"无论如何都不会有人出局"的情形 | 警告（可能是设计意图，但需标注） |
| **密令可解性** | 密令池中每条密令是否存在至少一条可达的达成路径 | 拒绝 |
| **密令互斥度** | 完全互斥的密令对占比是否超过阈值（防止必然全灭） | 拒绝或要求调整 |
| **隐秘规则配额** | `隐秘` 可见性修正件是否超过 2 条 / 是否含致死效果 | 拒绝 |
| **抽成合规** | `author_cut` 是否超过平台上限 | 拒绝 |
| **文本安全** | 文案的内容安全过滤 | 拒绝或送人工 |

### 7.2 闸门二：AI 试跑（自动，分钟级）

用 AI 编号（见 [08 文档](08-ugc-and-ai-host.md) §3）批量模拟 **N = 200 局**，采集统计指标：

| 指标 | 健康区间（草案） | 不健康的含义 |
|---|---|---|
| 平均致死率 | 应落在该 `day_tier` 的目标区间 | 与标注难度不符 |
| 致死率方差 | 不宜过低 | 过低说明结局被规则锁死，玩家决策无意义 |
| 首出局回合分布 | 不应集中在第 1 回合 | 开局即死，玩家没有参与感 |
| 平均局时 | 与 `expected_duration` 偏差 < 30% | 排期与匹配会出问题 |
| 密令达成率 | 各条密令达成率均落在 15%–70% | 过低=不可能，过高=送分 |
| 决策熵 | 玩家行动分布不应退化为单一最优解 | 存在"必胜策略"，博弈坍缩 |
| 收成分布 | 不应恒定为极值 | 生肖侧激励失效 |
| 级联告警次数 | 应为 0 | 存在规则打架 |

未通过的关卡包返回作者，**附带具体的统计报告与失败样本回放**——这既是质量闸门，也是**创作者教育工具**。

### 7.3 闸门三：灰度（人类小样本）

通过 AI 试跑的关卡进入**沙盒池**：

1. **沙盒房**：仅作者与其邀请的编号可进入，不消耗真实余命（记账但不结算）。
2. **灰度池**：向少量自愿尝鲜的编号开放，真实结算但**余命波动上限减半**。累计 30 局有效样本后评估。
3. **正式池**：灰度期评分与统计达标后进入，开始按正常抽成。

### 7.4 闸门四：持续监控与下架

进入正式池后，关卡仍受**持续监控**：

| 触发条件 | 处理 |
|---|---|
| 评分连续下滑至阈值以下 | 降权推荐 |
| 中途退出率异常升高 | 自动标记复查 |
| 致死率漂移超出标注区间 | 强制重新校验（通常因引擎版本升级） |
| 举报累计超过阈值 | 人工复审 |
| 确认存在漏洞利用 | 立即下架，冻结该包已产生的抽成 |

**版本化策略**：作者修改已上架关卡时，产生新的 `pack_version`，**必须重新走闸门一与闸门二**。旧版本的历史对局日志保留其对应的包哈希，保证历史可重放不被破坏。

### 7.5 评分维度

不使用单一的"好评/差评"，而是**四维打分**（关卡结束后向玩家征集，可跳过）：

| 维度 | 问题 | 用途 |
|---|---|---|
| **公平** | 你输的时候，知道自己为什么输吗？ | 最重要的维度，低分直接降权 |
| **张力** | 有没有让你手心出汗的时刻？ | 核心体验指标 |
| **清晰** | 开局时你看懂规则了吗？ | 检测规则过载 |
| **叙事** | 主持人的演出是否加分？ | 反馈给 AI 主持人调优 |

造关者声望主要由**公平**与**张力**驱动，而非游玩次数——防止刷量型垃圾关卡挤占推荐位。

## 8. 未决问题

1. **修正件数量上限定在 8 条是否过紧？**
   8 条能保证玩家读得完，但可能限制"复杂规则怪谈"类关卡的表达。是否应按 `day_tier` 分级放宽（试炼层 4 条 / 崩坏层 12 条）？需要在 M1 用真实关卡验证。

2. **同层冲突的"代价更大者优先"是否会催生军备竞赛？**
   该规则鼓励玩家不断加码烧记忆去压过对手。这在戏剧性上很好，但可能导致高阶回响者在一局内烧光记忆。是否需要引入"单局记忆消耗上限"？如果引入，会不会削弱回响的关键时刻？

3. **`隐秘` 可见性是否应该彻底取消？**
   目前限制为 2 条且不得致死。但即便如此，未公开的规则依然会伤害玩家对公平的感知（评分第一维度）。取消它会损失"规则怪谈"的惊悚感，保留它会带来长期的信任成本。需要主创拍板取舍。

4. **AI 试跑的 N=200 局在成本上是否可接受？**
   AI 编号试跑需要消耗 LLM 调用（或退化为脚本 AI）。若用纯脚本 AI，统计结论对真人行为的代表性存疑；若用 LLM，200 局 × 10 编号的成本可能过高。是否采用"脚本 AI 跑 200 局做机械校验 + LLM AI 跑 10 局做体验校验"的双层方案？

5. **基础玩法模板是否永久封闭？**
   长期看，最优秀的造关者一定会想要新模板。是否应设立"模板提案"通道（作者提交设计文档 → 官方实现），并给予提案者永久署名与分成？这会显著改变创作者生态的天花板。
